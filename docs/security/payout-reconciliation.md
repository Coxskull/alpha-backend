# Internal payout reconciliation

Administrator-only queue: GET /api/payout-reconciliation?kind=settlement|earning&after=GUID&limit=20. Inspect: GET /api/payout-reconciliation/{kind}/{id}. Queue pagination uses ascending UUID primary keys and a maximum of twenty sources, with repeatable-read observations. Filter exceptions per page, not across a whole unbounded ledger; scan all pages for a complete review. New rows with UUIDs behind an existing cursor require a fresh pass.

Compares supported supplier/driver settlement sources against matching paid payout records, entrepreneur earnings against single-earning payout batches, recovery offsets against payee/type/currency/claim/global recovered totals, order attribution, audit history and payout references. Missing, duplicate, foreign-currency, mixed/legacy multi-earning batches, incomplete paid metadata and ledger mismatches are exceptions. Pending sources without paid records are not proof of completed payouts. Historical payout rows without a source are outside this source-first queue; inventory those separately before acceptance. Each order/batch/target's inspected evidence is bounded at 200 rows; larger records require manual review. These are internal records, not provider/bank confirmation or a reconciliation of every general-ledger account.

POST /api/payout-reconciliation/{kind}/{id}/captures accepts {id: unique UUID, fingerprint: current 64-character hash}. It writes only an append-only observation to existing immutable audit_logs. It never changes financial balances, payout/claim/hold status, or source references. Exact request replay returns the original snapshot even after source evidence changes; changing actor/source/fingerprint on the same UUID fails. Fresh stale fingerprint capture fails; refresh and choose a new observation. A session advisory lock with an explicitly held connection serializes capture-ID replays before the repeatable-read transaction; payout operations are not blocked by this lock. Captures reflect a coherent database observation, not a promise that later state remains unchanged. GET /{kind}/{id}/history is bounded and scoped to the immutable versioned capture payload. Existing UPDATE/DELETE/TRUNCATE SQL audit guards apply; privileged database owners can bypass guards.

Operator procedure: scan both queues, inspect exceptions with accounting evidence, preserve a snapshot, and escalate discrepancies to the existing hold/review process. Do not re-record payouts to resolve discrepancies. Capture is not signoff or a release. Unknown capture response: check history or explicitly replay the same capture UUID/fingerprint; no automatic POST retries. No independent human, external provider, bank, hosted schema/role, or production acceptance is implied. No new schema migrations, providers, credentials, bank transfers, or production access are needed.

Operational limitations: audit history lookup uses existing audit storage rather than a new dedicated indexed journal; benchmark realistic isolated data volumes before hosted acceptance. No all-accounting-ledger completeness claim is made. Auth uses both token admin authorization and current database active-role checks. Snapshot fingerprints include raw related records and are versioned by audit payload prefix. Original-order/new-allocation holds remain intact.

Oversized source isolation: queue rows that exceed an evidence bound retain their resource ID/status with inspectionAvailable=false, manual_review_scope_exceeded and null monetary/reference fields. They are queue markers, not financial observations, and cannot be inspected/captured through this bounded workflow. Only that source is quarantined; remaining sources and cursor paging continue. Other operational/query failures still fail the request rather than being silently treated as manual scope limits. Existing v1 capture payloads default inspectionAvailable=true when read, as only actual observations were previously capturable; stored history is never rewritten.

Record-first supplement: GET /api/payout-reconciliation/records?kind=supplier|driver|batch&after=GUID&limit=20 scans payout records for missing sources, unexpected source counts, source paid-state/currency mismatches, invalid currency/negative amounts and unpaid record status. Attribution requires the exact order, role and payee; currencies are compared, never netted together. Batch records cannot independently identify an order/payee, so those fields remain null. This is a read-only exception inventory, not a complete amount/reference/bank verification; continue the existing source-first review for supported linked records. No capture, attach, repair, approval, transfer or hold-release operation is provided. Pages are exception-filtered on the server and have independent per-kind UUID cursors. Newly inserted UUIDs behind a cursor require a fresh scan. Correlated source-count query plans must be benchmarked/index-reviewed on realistic isolated volumes before hosted acceptance. Preserve evidence through the existing reviewed accounting process; do not guess a missing attribution or create a replacement payout.
